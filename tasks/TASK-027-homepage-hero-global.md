TASK ID: TASK-027
PHASE: Phase 2
GOAL: Make the homepage hero (image + eyebrow + heading + body + CTA label/href) editable from the Payload admin via a new `HomepageHero` Global. Today these values are all hardcoded in `src/app/(frontend)/page.tsx` — every change requires a code edit. After this lands, dad and sister can edit the hero from the admin without filing a code request.

CONTEXT:
Neal flagged this gap during TASK-025: "I have added all the images to r2. How do I change the homepage hero image?" Right now the answer is "edit the constant in `page.tsx` and push." That's not a sustainable workflow for non-technical admins.

Payload Globals are single-document configs (one row in the DB, no list view in admin — just an "Edit" form). Standard pattern for site-wide settings like hero copy, footer copy, contact details, social links. We're starting with just the homepage hero; future globals (FooterContent, SiteSettings) can follow the same pattern.

This task touches three blocklisted areas, so it's **all Claude Code work**:
- `src/payload.config.ts` (registers the global)
- `migrations/**` (new migration for the global's DB row)
- Otherwise just the new global config file + a homepage `findGlobal` call.

Design constraint: **all hero fields are OPTIONAL with fallbacks to current hardcoded values.** This guarantees graceful degradation. If the admin hasn't set up the global yet (or only fills in some fields), the homepage still renders cleanly with the current artisan copy and image. As fields get filled in, they override the fallback one at a time.

**4. Wire the homepage to the global (`src/app/(frontend)/page.tsx`).**

Convert from a sync server component to async (already is — exports a default function with metadata, but the body is sync). Fetch the global, build the prop values with fallback chains, render `<Hero>`.

```tsx
import type { Metadata } from "next";
import { getPayload } from "payload";

import config from "@payload-config";

import Hero from "@/components/storefront/Hero";
import ProductCard from "@/components/storefront/ProductCard";

export const metadata: Metadata = {
  title: "Nepali Threads",
  description:
    "Handmade clothing from Nepal. A small studio releasing one collection at a time.",
};

const FALLBACK_IMAGE =
  "/migrated-product-images/Facetune_11-06-2024-18-51-27.jpeg";

export default async function HomePage() {
  const payload = await getPayload({ config });
  const hero = await payload.findGlobal({ slug: "homepageHero" });

  const heroImageObj =
    hero.image && typeof hero.image === "object" ? hero.image : null;

  const heroProps = {
    imageSrc: heroImageObj?.url ?? FALLBACK_IMAGE,
    imageAlt:
      heroImageObj?.alt ??
      "A handwoven wool cardigan draped over a wooden chair",
    eyebrow: hero.eyebrow ?? "New collection",
    heading: hero.heading ?? "Made by hand in Nepal",
    body:
      hero.body ??
      "A small studio releasing one collection at a time, woven with the same care our families taught us.",
    cta: {
      label: hero.ctaLabel ?? "Shop the collection",
      href: hero.ctaHref ?? "/shop",
    },
  };

  return (
    <>
      <Hero {...heroProps} />
      {/* rest of homepage unchanged */}
    </>
  );
}
```

Notes:
- `payload.findGlobal({ slug: "homepageHero" })` always returns a doc — Payload creates one on first read with empty/default values. So we don't need notFound() handling.
- The fallback chain uses `??` (nullish coalescing) so empty strings DON'T fall back. If the admin saves an empty string explicitly, that's their choice (the field gets stored as null in Postgres anyway since nothing is set; Payload returns null for unset fields). The fallback applies on null/undefined only.
- Wait — Payload may return empty strings rather than null for text fields. Test this when implementing: if `hero.eyebrow === ""` returns and we want the fallback to kick in for empty strings too, use `||` instead of `??`. Lean toward `||` for hero fields — empty string in admin almost always means "I cleared this, use default."
- The image fallback path `/migrated-product-images/Facetune_11-06-2024-18-51-27.jpeg` is the original PLACEHOLDER_IMAGE. Rename the constant to `FALLBACK_IMAGE` to make its purpose clearer.
- Existing "Recent work" section + mission section continue to use the same hardcoded data they always have. Only the Hero is editable via the global. Future tasks can extend this same Global with additional fields if those sections become editable.
